# 模块 07 参考答案

## A1

a) real = 墙上时钟经过的时间；user = 用户态代码消耗的 CPU；sys = 内核态（syscall、驱动）消耗的 CPU。
b) real ≫ user+sys：CPU 没在算，时间耗在**等待**——磁盘 IO、网络、锁、睡眠。
c) user+sys > real：多个线程/进程**并行**跑满了多核（各核 CPU 时间求和自然超过墙钟）。

## A2

- 追踪型：记录**每一次**函数调用（cProfile）——信息全（调用次数、调用图），但开销大，会拖慢被测程序
- 采样型：定时中断**看一眼**程序此刻的调用栈（perf）——开销极小，跑得久结果越准，适合不能被拖慢的生产/比赛环境
- 场景：Python 脚本分析用 cProfile/line_profiler；C/C++ 与生产环境用 perf

## A3

因为**直觉的热点经常是错的**：花一下午优化了占 2% 时间的函数，总耗时几乎不变。正确循环：`perf record / cProfile → 数据指出最热函数 → 只优化它 → 重新测量验证收益`——每一步都有数字背书。

## A4

"程序到底在内核里干什么"——比如程序卡住不动：strace 一看它阻塞在 `read()` 某个文件描述符 / `connect()` 某个 IP， pdb 看不到 syscall 层，strace 直接回答"卡在哪条系统调用上"。（例：排查"为什么配置文件没生效"——strace 显示程序根本没 open 你以为的那个路径。）

## A5

标准顺序（实战验证过的版本）：
1. **读完整报错**（最后一行+第一行错误常在不同位置）
2. **最小复现**：收缩到最小输入/最短脚本
3. **定位**：打日志 / 断点单步 / 二分注释——缩小嫌疑范围
4. **一次只改一个变量**，验证修复
5. 修完问自己"为什么会发生"，补一个防复发的测试/静态检查

## B1

断点处 `p i, j, arr` 会显示当前外/内层进度与数组现状（如 `0, 3, [1, 3, 2, 5, 4]`）。内层应为 `range(len(arr) - 1 - i)`——每轮末尾已就位的 i 个元素无需再比较；原版每轮都扫到头，做了约两倍的比较次数。（pdb 操作：`b 3` 下断点、`c` 运行到断点、`p` 查、`n` 步过、`q` 退出。）

## B2

shellcheck 会报 SC2045（遍历 `$(ls)` 的输出）之类：**解析 ls 的输出是反模式**——文件名含空格/换行时，`$(ls)` 按空白拆词，"My Song.mp3" 变成 "My" 和 "Song.mp3" 两段，脚本直接坏。正确写法：`for f in *.mp3`（glob 由 shell 安全展开——模块 02 的知识闭环）或 `find -print0 | xargs -0`。

## B3

- curl：real 数秒、user/sys 毫秒级——**网络等待型**（CPU 几乎闲置）
- grep -r /usr/include：real ≈ user+sys 且数值可观——**计算+IO 混合型**（CPU 在干活，还读了几万个文件）
形态先于数值：先看三者的**比例关系**再谈优化方向。

## B4

- 热点是 `fib` 自身：35 时被调用约 **930 万次**（每 fib(n) 递归展开成一棵二叉树）
- 加 `@functools.lru_cache(maxsize=None)` 后：每个 n 只真算一次，调用次数降到 **约 2×35 次**，耗时从秒级到毫秒级
- cProfile 输出重点列：`ncalls`（次数）、`tottime`（自身耗时）、`cumtime`（含子调用耗时）——热点按 tottime 排序

## C1

rg 通常快数倍到数十倍（自动跳过二进制/隐藏/.git、并行、更快的正则引擎）。`--warmup 3` 先空跑 3 次不计时：把**文件系统缓存**焐热（第一次跑的数据都在磁盘上，后几次在内存里）——对比的是工具本身而不是磁盘冷热，冷启动数据会污染结论。

## C2

`lsof | grep LISTEN` 输出巨大时用 `lsof -i :4444` 或 `lsof -iTCP -sTCP:LISTEN` 精确过滤；`ss -tlnp` 一条列出所有监听端口与进程（-t TCP -l 监听 -n 数字端口 -p 进程）。找到 PID 后 `kill <PID>`（默认发 SIGTERM——模块 05）。

## C3

`stress -c 3` 在 htop 里是 3 个 100% 的 stress 进程，散布在任意核上；`taskset --cpu-list 0,2` 后 3 个进程**挤在 0、2 两个核**（每核约 150%），其他核空闲。CPU 亲和性的意义：HPC 里把线程钉在核上避免迁移开销、或把干扰进程隔离到别的核——HelloHPC 第 5 题的 taskset 跑分就是直接考点。
