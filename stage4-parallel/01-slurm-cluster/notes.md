# 模块 01：集群与 Slurm 调度

> **来源**：Slurm 官方 Quick Start（https://slurm.schedmd.com/quickstart.html）+ 交我算/HelloHPC 实题语境（kp_interact / kp_run 队列、128 核单机、module 系统）
> 进入比赛硬技能区第一课：**不会用集群，一切优化都无处落地**。

## 0. 一句话定位

集群 = 几百台机器 + 共享存储 + 一个**调度器**；Slurm 就是那个调度器——集群的"排队叫号系统"。你向它**申请**资源（多少节点、多少核、多长时间），它安排你的程序到某台计算节点上跑。

## 1. 集群解剖：三种角色

```
你的电脑 ──ssh──> 登录节点（login node）──调度──> 计算节点 × N（compute node）
                        │                            ▲
                        └──── 共享文件系统（家目录/scratch）──┘
```

- **登录节点**：你 ssh 进去的地方。只用来**编辑代码、编译、提交作业、看结果**——它像前台接待，全体用户共享少数几台，**在上面跑重活会被管理员杀掉**（还会拖慢所有人）。
- **计算节点**：真正干活的机器，几十到几千台。你**不能直接 ssh**（除非调度器批准），只能通过 Slurm 把任务派上去。
- **共享存储**：家目录（`~`）所有节点都看得见（所以登录节点编译的程序，计算节点能直接跑）；大文件放 scratch（快但可能定期清理）。

**为什么要有调度器**：上百个用户抢上千个核，谁先用、用多久、怎么记账？靠排队系统统一分配——就像医院挂号，不能谁跑得快谁占手术室。

## 2. Slurm 核心命令（六件套）

| 命令 | 干什么 | 类比 |
|------|--------|------|
| `sinfo` | 看队列（分区 partition）和节点状态 | 看门诊有哪些科室、开没开 |
| `squeue` | 看排队中的作业（自己的加 `-u $USER`） | 叫号屏幕 |
| `sbatch 脚本` | **提交批处理作业**（正式姿势） | 挂号排队，到号自动进 |
| `srun 命令` | 申请资源**直接运行**（可交互） | 插队立即看诊 |
| `salloc` | 只申请资源，给你一个**落在计算节点上的 shell**（调试用） | 借个诊室自己折腾 |
| `scancel 作业ID` | 取消作业 | 退号 |
| `sacct` | 查历史作业的用时/状态/退出码 | 病历本 |

## 3. 作业脚本解剖（考试直接考这个）

```bash
#!/bin/bash
#SBATCH -J graph500          # 作业名（squeue 里显示）
#SBATCH -p kp_run            # 队列/分区（partition）：正式跑
#SBATCH -N 1                 # 节点数：1 台机器
#SBATCH -n 1                 # 任务数（进程数）：1 个
#SBATCH -c 128               # 每个任务的核数：128 核吃满单机
#SBATCH -t 00:40:00          # 时限 40 分钟（超时强杀！）
#SBATCH -o g500_%j.out       # 输出文件，%j = 作业 ID

module load compiler/gcc     # 加载环境模块（见下节）
make                         # 编译
./graph500_reference_bfs_sssp 18   # 运行
```

**要点**：
- `#SBATCH` 行是**给 Slurm 看的注释**——bash 忽略它（# 开头是注释），调度器在提交时扫走当参数。等价于命令行 `sbatch -J graph500 -p kp_run ...`
- `-t` 是**生死线**：HelloHPC 里 WRF 编译限 60min、运行限 20min、graph500 超 40min 强制结束——预估时长要留余量
- 脚本里的命令就是普通 bash：你学过的 cd/make/time/重定向全部适用
- **module 环境不继承**：交互 shell 里 load 过的模块，sbatch 脚本里要**重新 load**（每个作业是干净环境）

## 4. 分区（队列）：kp_interact vs kp_run

HelloHPC 平台的两个队列，代表集群通用设计：

| 队列 | 用途 | 特点 |
|------|------|------|
| `kp_interact` | 交互调试 | 排队快、时限短、资源少 |
| `kp_run` | 正式运行 | 资源足（128 核）、排队长 |

纪律：**调试用 interact，跑分用 run**。在 interact 里跑正式作业要么资源不够要么跑不完。

## 5. module：集群的"环境货架"

集群上有 5 个版本的 GCC、3 套 MPI、各版本 CUDA——打架了怎么办？module 系统按需上架：

```bash
module avail          # 货架上有什么（先看再拿）
module load gcc/11.2  # 把 GCC 11.2 挂进当前 shell 的 PATH
module list           # 我拿了哪些
module purge          # 全部下架（脚本开头常用，保证干净起点）
```

本质：module load 就是在改你 shell 的**环境变量**（PATH、LD_LIBRARY_PATH 等）——第 2 讲"配置即代码"思想的集群版。

## 6. 常见误区清单

1. **在登录节点跑计算**——被杀 + 拖累全员；重活必须 sbatch/srun
2. `-t` 写太紧——作业跑到 39 分钟被强杀，前功尽弃；写太松——排队优先级可能变差
3. 忘写 `-o xxx_%j.out`，输出全进默认的 `slurm-作业号.out`，找不到还以为没跑
4. sbatch 脚本里**不重新 module load**——编译器/MPI 都不在，make 直接报错
5. `squeue` 看不到自己作业——加 `-u $USER` 过滤；作业秒消失先看输出文件里报了什么错
6. 单机多核任务只申请 1 个核，OpenMP/多线程跑不起来——**核是申请来的，不是默认给的**

## 7. 与超算比赛的联系

- HelloHPC **WRF/Graph500/绳网仿真**全是同一模式：写 build+run 一条龙脚本 → sbatch 提交 → 计时得分
- Graph500 明确要求脚本里含 make；WRF 分编译限时/运行限时两段——`-t` 要按段设
- 平台是 ARM 鲲鹏：module 里选 aarch64 版本，x86 的二进制拿过来跑不了
- 交作业前本地自测：题目都带 evaluate.py，先跑它再提交
