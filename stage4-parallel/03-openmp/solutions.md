# 模块 03 答案：OpenMP

## A 概念题

**A1** `parallel` 区域：每个线程把大括号内代码**完整复制执行一遍**（4 线程 = 4 遍）；`parallel for`：迭代被**切成块分给线程**（4 线程共执行 1 遍，各拿约 1/4）。前者是"复制"，后者是"分工"——所以 parallel 后面常包 for（组合指令 `parallel for` 就是把两者合一）。

**A2** 病灶：`count++` 是"读-改-写"三步，多线程同时做会互相覆盖（写冲突）。两种修法：
```c
// 修法1：原子（轻，单条内存语句）
#pragma omp atomic
count++;
// 修法2：归约（更优——无锁，各线程私有计数，结束合并）
#pragma omp parallel for reduction(+:count)
```
取舍：atomic 每次都要抢那一个变量（串行化了累加点）；reduction 各加各的最后合并，冲突为零——**本场景 reduction 完胜**。

**A3** 归约三件事：① **私有化**——每线程一份变量副本，初始化为单位元（`+`→0，`*`→1，`max`→-∞）；② **分工**——迭代切块，各线程只更新自己的副本；③ **合并**——区域结束时所有副本按运算符合并回原变量。
浮点末位不一致的原因：浮点加法不满足结合律，`(a+b)+c ≠ a+(b+c)`；归约的合并顺序（哪个线程的副本先合并）不确定，末位有效数字因此漂移。**不是 bug，是浮点归约的固有特性**——除非题目要求按位一致（那要么单线程算该部分，要么用整数/定点，要么祈祷出题人给了容差）。

**A4** 选 `schedule(guided)`（dynamic 也可，guided 更优）。默认 static 均切会把"大计算迭代"切到同一个线程——最倒霉的线程拖着全员陪跑（其他线程在 barrier 前干等）。dynamic/guided 让快的线程多抢活，总时长趋近"最重单块"而非"最重整块"。guided 大块起步小块收尾，兼顾调度开销与均衡，是不均匀负载的首选。

**A5** OpenMP：线程共享内存，直接读写同一地址空间；MPI：进程私有内存，靠显式消息传递交换数据。
① 向量内积：单节点内 → **OpenMP**（`parallel for reduction(+:s)` 一行搞定）；
② WRF 跨 2 台机器：两台机器内存不共享 → **MPI**（消息传数据）——真实 WRF 其实是 MPI+OpenMP 混合：机器间 MPI，机器内 OpenMP。

## B 动手题

**B1** 
- 第一次 `./hello`：打印"默认线程数"行（WSL 上通常=物理/逻辑核数，比如 8 行）
- `OMP_NUM_THREADS=2`：2 行（环境变量说了算）
- 忘 `-fopenmp`：**1 行**——gcc 把不认识的 pragma 当注释，程序退化成串行版，只有主线程打印一遍
- 不报错不警告的原因：`#pragma` 本来就是给编译器的"建议"，C 标准规定不认识的 pragma 可以忽略——OpenMP 特意利用这个规则设计出"可串行性"（指令拿掉程序仍正确）。隐患：**静默变串行**——你以为在并行，其实在裸奔，且没有任何提示。性能不达预期时第一件事查编译命令。

**B2** `total`：并行区外的累加变量，多线程共享 → 写冲突元凶 → 改 `reduction(+:total)`。`w`：循环内临时变量，各线程本该有自己的 → 默认共享 → 线程间互相踩（虽然值相同，但语义错且阻碍优化）→ 改 `private(w)`。
```c
double total = 0;
#pragma omp parallel for reduction(+:total) private(w)
for (int i = 0; i < 1000; i++) {
    double w = sqrt((double)i);
    total += w * data[i];
}
```
更优雅：把 `w` 声明挪进循环体内（块作用域自动私有），total 单独 reduction。

**B3** 参考结果（数值因机器而异，量级关系是重点）：
- serial ≈ 200-400 ms；1 线程 OpenMP ≈ 同级；8 线程 ≈ 40-80 ms
- 加速比 ≈ **3-5 倍，远不到 8**
- 原因：这题是**访存密集（memory-bound）**。每次迭代 2 次读（16B）+1 次乘加（~0.5 flop），算术强度 ≈ 0.03 flop/B——CPU 的乘加能力根本用不完，8 个核抢同一条内存带宽。带宽只有核带宽的几倍，所以加速比封顶在"带宽倍数"。**结论：加速比的上限不总是核数——先问数据从哪来（roofline 思维）**。验证法：把 N 缩小到 1e6（数据全进缓存），加速比会显著改善。

**B4** 预期排序（负载不均越严重差距越大）：`static` 最慢（大计算迭代扎堆某些块）→ `dynamic` 显著改善 → `guided` 通常最优或持平 dynamic（前段大块省调度开销、后段小块填缝）。若三者在你的机器上差异不大，把 heavy() 加重或迭代数加大再试——**实验现象依赖负载不均程度，这也是实验报告该写的"条件"**。

## C 挑战题

**C1** 参考实现：
```c
double pi_omp(long n) {
    double dx = 1.0/n, s = 0.0;
    #pragma omp parallel for reduction(+:s)
    for (long i = 0; i < n; i++) {
        double x = (i + 0.5) * dx;
        s += 4.0 / (1.0 + x*x);
    }
    return s * dx;
}
```
- n=1e9 时误差 ~1e-9 量级（中点法 O(dx²)）
- ③ 加速比更接近核数的原因：`4/(1+x²)` 含除法，算术强度比 B3 的纯乘加高一个量级——计算占大头，内存不再是瓶颈，核数即上限（计算密集型特征）。B3 vs C1 正好构成 memory-bound 与 compute-bound 的对照实验。

**C2** 预期现象：相邻版本明显慢于远距版本（常见 2-10 倍差，机器而异）。
伪共享机制：缓存一致性以**缓存行（64B）**为单位——`c[0]` 和 `c[1]` 相邻 8 字节，同住一行。线程 0 写 `c[0]` 时，该行在核 1 的缓存被判失效；核 1 写 `c[1]` 又把核 0 的失效——两个变量明明无逻辑共享，一致性流量却让它们"隔空打架"。
修法：让热点变量各占一行——`alignas(64) long c[2];` 或在中间填充 `long pad[7]`。教训：**并行性能问题可以毫无算法层面的原因**，剖析工具（perf c2c）和缓存行意识是进阶必修。

**C3**
1. **外层空间循环可并行**：`new[i]` 只依赖上一轮的 `old[i-1]、old[i+1]`，同一轮内各 i 相互独立。**内层时间步循环绝不能并行**——第 t+1 轮依赖第 t 轮的完整结果（时间轴上的循环携带依赖）。
2. 不合算。每轮迭代 spawn/join 一队线程，1000 轮就是 1000 次，线程创建开销在总耗时里占比可能压过计算。改进：① `#pragma omp parallel` 放在时间循环外（线程只创建一次），循环内用 `#pragma omp for` 分工；② 或者每 K 轮才重新分区。标准写法：
```c
#pragma omp parallel
for (int t = 0; t < 1000; t++) {
    #pragma omp for
    for (int i = 1; i < N-1; i++) new[i] = (old[i-1]+old[i+1]) / 2;
    #pragma omp single          // 隐式 barrier 已保证安全，交换指针只需一人
    { double *tmp = old; old = new; new = tmp; }
}
```
3. 这题敢开：运算只有加法和除二，`-ffast-math` 允许的"重排/简化"对纯加法不改变结果（加法交换序变化最多影响末位，且题目给的 1e-6 容差远大于此）。带 `sin/cos` 的题要小心：`-ffast-math` 会替换成低精度近似库函数，误差可能超容差——**敢不敢开的判据 = 变换引入的误差是否在题目容差内**。OceanSim 给容差就是这个用意。
