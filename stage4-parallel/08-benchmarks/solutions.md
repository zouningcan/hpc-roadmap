# 模块 08 答案：HPL/HPCG 基准

## A 概念题

**A1** HPL 测稠密线性方程组（高斯消元，GEMM 主导）的算力上限；HPCG 测稀疏迭代求解（SpMV/平滑/多重网格）。对比：HPL 算术强度 O(n)（越大越接近算力上限）、负载规则（稠密分块）；HPCG 强度 ~0.25 flop/B 级（每行非零元只用一次）、不规则（稀疏模式）——**bandwidth-bound + 随机访存**。所以 HPCG 卡在内存带宽和访存延迟上，只能兑现算力的零头。

**A2** 效率 = 75/100 = **75%**（好集群的正常水平）。嫌犯三连：① BLAS 库不是本硬件最优（换库 10-30%）；② N/NB/网格没调好（通信/负载失衡）；③ 频率没锁/NUMA 没绑核/噪声进程。（也可能：内存带宽不足的 CPU 天生效率低。）

**A3** N=问题规模（内存占用，定分母）；NB=分块（对齐 BLAS 最优）；P×Q=进程网格（通信拓扑）。顺序：**先按内存公式定 N → 固定 N 扫 NB → 固定 N/NB 扫 P×Q → 回头微调 N**。理由：N 是分母、收益最大且受内存硬约束，先定；NB 影响 GEMM 效率，次之；网格只在前面都对了之后精修通信——收益递增顺序 = 调参顺序。

**A4** 100%：溢出/交换/通信缓冲被挤——暴跌；50%：算力浪费（HPL 大 N 才有高效率，规模不够效率上不去）。估算：`N ≈ sqrt(M_bytes × 0.8 / 8)`（双精度 8B，系数矩阵 N² 个元素）。例：256GB 节点 × 0.8 / 8 = 25.6e9 → N ≈ 160000。

**A5** BLAS 是 HPL 计算的 95%+——库的 GEMM 快慢直接乘到总分；不同厂商库在自家硬件有 10-30% 差距，且免费换（重新链接）。前三名 oneMKL/BLIS 各自绑定 Intel/AMD 硬件——**软件栈与硬件是配套设计**的行业事实：没有"万能最快库"，只有"本机最快库"。

## B 动手题

**B1** 关键点：
- Make.wsl 必改项：`ARCH=wsl`、`TOPdir=解压路径`、`MPdir`/`MPI_HOME`（OpenMPI 路径）、`LAdir=/usr/lib/x86_64-linux-gnu`、`LALIB = -lopenblas`（BLAS 链接）
- 正确性标志：结果表每行末尾 `PASSED`；残差 `||Ax-b||` 相对量 ~1e-13 级
- Rpeak 例：4 核 × 3.0GHz × 16 DP FLOPs/周期（AVX2 FMA：2×8）= 192 GFLOPS；效率 = Gflops/192
常见坑：root 跑 mpirun 要 `--allow-run-as-root`；OpenBLAS 自己开多线程会跟 MPI 打架（`OPENBLAS_NUM_THREADS=1`）——**两个并行层打架**是 HPL 经典事故。

**B2** 参考形态（8GB 内存 WS L 示例）：
| N | 2048 | 4096 | 8192 | 12288 | 16384 |
|---|------|------|------|-------|-------|
| Gflops | 低（规模不够，GEMM 效率低） | ↑ | ↑↑ | 峰值区 | 内存压力大/换页↓ |
峰值落在"N² ×8B ≈ 内存 80-90%"附近；再往上：物理内存吃满 → 换页/分配失败 → 悬崖。曲线是"爬坡-平台-悬崖"。

**B3** NB 表预期：单峰曲线，峰值在 192/256 附近（OpenBLAS 常见最优），与 CPU 的缓存/流水线设计相关——BLAS 内部 GEMM kernel 按 NB 切块，块大缓存装不下、块小开销占比大。P×Q 表预期：1×4 ≈ 2×2 > 4×1（4×1 最差）；方形偏好：HPL 的广播沿行/列进行，P≈Q 时两级通信量最均衡（通信代价 ∝ |P-Q| 方向的失衡）。两题都指向：**参数最优值由底层硬件决定，扫参是唯一诚实的找法**。

**B4** PASS 标志：结果表行尾 `PASSED`（残差检查通过）。危险信号：PASSED 但残差 1e-6 级（正常 ~1e-13）——说明数值路径有问题（库越界/精度配置错），规模一大可能翻车；比赛语境下残差异常=裁判可能判无效。**先对再快的"对"要量化到残差量级，不是看见 PASS 就放心。**

## C 挑战题

**C1** ① 三 kernel：SpMV（稀疏矩阵向量乘）、SymGS（对称 Gauss-Seidel 平滑）、多重网格的 restriction/prolongation（+点积等向量操作）。② 优化目标完全不同：SpMV 是流式随机访存，管的是 CSR 布局/预取/并行度/同步开销——HPL 的 NB/网格在这里毫无用武之地（参数不存在）。③ 比值 HPCG/HPL 通常 1-3%：比值高的机器（带宽强、真实负载好）才是"全能选手"——SC/ISC 把 HPCG 计分就是逼大家重视这个比值。

**C2** ① 全开：2×280 + 4×300 = 560+1200 = 1760W CPU/GPU，加内存/网卡/风扇 ~400-600W ≈ 2300W——未超 3000W（本题数值设计如此）；若 GPU 为 600W 版则 3560W 超支 560W。② 合规方案：a) GPU 限频 70%（功耗 ~线性下降，算力 ~降 10-20%——频率-功耗的非线性让限频"性价比高"）；b) 砍 GPU 数（4→3，算力 -25%，功耗 -600W）。对比：限频保拓扑（TP 并行度）损失小、砍卡伤并行规模。③ HPL 更敏感（全程满功率轰炸，瓦特-性能直接挂钩）；AI 推理赛题常 burst 式。留 10% 余量：防峰值瞬时超限跳闸（功率尖峰/风扇启动）——**跳闸 = 全场清零，余量是保险费**。

**C3** 
1. 禁重定向：TEPS 结果在 stdout/stderr 里，OJ 直接读原始输出——重定向会破坏输出流（也可能藏猫腻，如结果伪造）；基准的输出是契约
2. 三排查：① 编译选项（-O3/-march、BLAS/图库链接对不对）② 运行参数（scale=18 的规模、生成图参数、验证开关是否被关——题面要求不许跳过验证）③ 并行方式（线程/进程数是否吃满 128 核、绑定 NUMA——htop+perf stat 判型）
3. 异同：同——都是"编译→配参→跑→读分"的基准工序、都要单变量扫参；异——HPL 的参数在 HPL.dat（文本、结构化），Graph500 的"参数"是命令行 scale 与环境变量（离散、要写脚本循环跑）——**写 wrapper 脚本自动扫参**（本题要求的 graph.sh 本质）就是基准调优的通用形态，HelloHPC 用它考 Slurm+脚本+调优三合一。
